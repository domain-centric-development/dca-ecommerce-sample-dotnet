## Criteria
- authorized-payment-moves-to-review: met. The shop the E2E suite starts is configured with the stub's address, so `RestPaymentProvider` sends one `POST /payments` for the session total and currency. A `201` with a reference moves the session on, and the review page shows.
- refused-payment-stays-at-payment: met. A `402` becomes `PaymentResult.Refused`, the use case raises `PaymentInitiationFailedException`, and the controller re-renders the payment page (200) with "The payment was refused. Please choose another way to pay.".
- slow-provider-counts-as-unavailable: met. The named client's 2 s timeout abandons the 5 s answer, and the adapter reports `Unavailable`. The use case raises `PaymentProviderUnavailableException`, and the page shows "The payment provider is not available right now. Please try again later.". The response arrives well under the test's 4 s bound.

## Deviations from the plan
- `IPaymentProvider.PaymentResult`: the plan proposed `Refused`/`Unavailable` factories next to the existing ones. The result now carries a nested `PaymentOutcome` enum, and `Failed` is gone (its only caller, the stand-in, now says which kind it means). The positional `bool Success` became a derived property. No caller outside the Checkout context existed.
- `RestPaymentProvider`: a singleton that takes `IHttpClientFactory` and uses a named client, not a typed `HttpClient`. The provider registry is a singleton holding its providers, so a typed (transient) client would have been captured for the process lifetime.
- `SubmitPaymentUseCase`: logs the reason for an unavailable initiation. The adapter logs as well, but the use case is the place that knows the provider id.
