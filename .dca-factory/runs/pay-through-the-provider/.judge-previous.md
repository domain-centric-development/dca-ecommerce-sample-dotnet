# Judge — pay-through-the-provider

## Verdict
verdict: story-conflict

The code meets all three criteria. The plan's design holds: the port result names the three outcomes, the REST
adapter is the anti-corruption layer, the remote call stays before the transaction, and the incoming web adapter is
the one translation site. One major finding remains, and no build round can fix it. The new browser test has no
scenario in the shared specification, and only the user may write one. See `## needs-human`.

## Considered and dropped
- Product description `## Not part of the product` names "Real payment": dropped. The change adds the REST integration
  that `project/tech.md` `## Integrations` lists. No configuration sets `Checkout:PaymentProvider:BaseUrl` (no
  `appsettings*.json`, compose or Dockerfile names it), so the shipped shop still pays with the stand-in, as
  `project/product.md` `## Qualities` says ("a stand-in in the sample").
- Glossary `PaymentProviderNotFound · PaymentProviderUnavailable · PaymentInitiationFailed`, which says "The provider's
  own reason travels through unchanged", while the page now shows fixed texts: not a code defect. The reason still
  travels on `PaymentInitiationFailedException` and in the log. The plan's glossary proposals give the new wording to
  the document stage.
- Two warning logs for one unavailable payment (`RestPaymentProvider.Unavailable` and `SubmitPaymentUseCase`): dropped.
  The use case adds the provider id and is the only log for the stand-in's outage. That is duplication with a reason,
  not a carried decision.
- `RestPaymentProvider.IsAvailableAsync` always answers `true`, and `ConfirmPaymentAsync` answers success without a
  call: dropped. The contract has no such endpoints, the port allows it, and the plan records it.
- `CheckoutPageController.CustomerMessage` switches on exception type: dropped. It is the context's one failure
  translation site, and choosing what the customer is told is exactly its job (hexagonal: translation at the edge).
- Integration tests read the rendered HTML with regexes: dropped. They are integration tests at the level the plan
  chose, not end-user tests standing in for the browser. The happy path is driven in Playwright.
- `ProviderPaymentE2eTest` fails against a shop started elsewhere (`E2E_BASE_URL`), because that shop is not pointed
  at the stub: dropped. This follows the answer to `pay-through-the-provider-01` (the suite brings its own shop and
  dependencies).
- Test levels: the happy path is the only browser test. The changed adapter (`RestPaymentProvider`) is passed through
  by six integration tests against a WireMock.Net stub. The unit tests' `AnsweringPaymentProvider` stands in for the
  port only at the use-case level, while the adapter itself is integration-tested. No test-level finding.
- Timeout handling: `catch (OperationCanceledException) when (!cancellationToken.IsCancellationRequested)` separates
  the client's own 2 s deadline from the caller's cancellation, as the plan requires. Correct.
- Everything the architecture suite enforces (layer direction, naming, context map freshness) was left to the gate,
  which passed 129/129.

## Criteria re-checked
- authorized-payment-moves-to-review: met. The browser test arranges a session at the payment step and an authorizing
  stub (`PaymentProviderStub.AuthorizesPayments`), then pays through the page. It asserts the review step
  (`review.IsOnPage`) and exactly one `POST /payments` whose amount and currency equal the total shown on the payment
  page. Behind it, `RestPaymentProvider` sends `snapshot.Totals.Total` (`SubmitPaymentUseCase`) and maps `201` with a
  reference to `Succeeded`.
- refused-payment-stays-at-payment: met. A `402` stub leads to `Refused`, then `PaymentInitiationFailedException`,
  then the payment page re-rendered (200, `payment-form`). `payment-error-message` holds exactly "The payment was
  refused. Please choose another way to pay."
- slow-provider-counts-as-unavailable: met. A 5 s delayed stub hits the 2 s client timeout
  (`PaymentProviderOptions.Timeout`), which leads to `Unavailable`, then `PaymentProviderUnavailableException`, then
  the payment page with "The payment provider is not available right now. Please try again later." The test also
  bounds the answer at under 4 s, so the late answer is abandoned, not awaited.
- Out of scope (webhook, refunds, cancellations): not delivered. `CancelPaymentAsync` makes no call.
