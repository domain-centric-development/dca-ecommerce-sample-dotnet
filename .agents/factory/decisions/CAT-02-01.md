# How should the gate get a running shop for CAT-02's browser test?

## Question

The plan gives `view-details-opens-the-product-page` the level **e2e** (Playwright). The characterization test
`DcaShop.E2eTests.ProductPageE2eTest#ViewDetailsOnACatalogueCardOpensThatProductsPage` is written. But the test
gate refused it twice with "was skipped rather than run" (`tasks/CAT-02/.gate-test.txt:18`). Every test in
`DcaShop.E2eTests` skips unless `E2E_BASE_URL` points at a shop that is already running. Neither the gate nor
the runner starts one. The test stage cannot fix this in the test sources without changing the suite's runner
convention, and the stage may not change runner conventions. How should the gate get a shop?

## Evidence

- `tests/DcaShop.E2eTests/E2eFactAttribute.cs:11-13` — `[E2eFact]` sets `Skip` when `E2E_BASE_URL` is empty.
- `tests/DcaShop.E2eTests/BaseE2eTest.cs:8` — the suite drives an external shop at `E2E_BASE_URL`. It does not
  host the app, and `DcaShop.E2eTests.csproj` does not reference `DcaShop.Web`.
- `.agents/factory/story-gate.py:1627-1632` — the gate fails a mapped test that the report shows as skipped.
  The gate runs `e2eTest:` in the environment it inherits. It does not use the profile's `run:` key to start the
  app (it uses `run:` only in the acceptance record text, `story-gate.py:4724`).
- `.agents/factory/factory.sh` sets no `E2E_BASE_URL` (grep: no hit).
- `.agents/factory/factory.profile.yaml` — "The end-user suite needs a running shop, so it stays out of
  [required]."
- The break for this test has the same problem. The gate applies it to a scratch copy, but the browser test
  drives whatever shop runs at `E2E_BASE_URL`, not that copy. So the break can turn the test red only if the
  shop is started from the scratch copy.

## Options

1. **Run the gate with a shop.** Start `dotnet run --project src/DcaShop.Web` and invoke the test gate with
   `E2E_BASE_URL=http://localhost:5080`, by hand or in the runner. No code changes. The break stays unverifiable
   by the gate (it runs against the live shop, not the scratch copy).
2. **Let the browser suite start the shop itself** when `E2E_BASE_URL` is unset: the fixture launches
   `DcaShop.Web` from the tree the tests run in, on a free port. That is a stack change to the suite (fixture,
   possibly a project reference) and belongs in its own change, not in this story. It makes both the test and
   its break observable at the gate.
3. **Cover the happy path at the integration level instead.** The plan is reopened and
   the happy path is checked over HTTP (`GET /products`, follow the card's "View Details", assert the heading),
   like the other four scenarios. This drops the browser check for this story.

## Recommendation

Option 2 as a separate tooling change, since it closes the gap for every future story with a browser test and
lets the gate verify breaks. Until it lands, option 1 unblocks CAT-02.

## Answer
answer: The end-user suite now starts the shop itself, in the test process and on a free port — nothing has to run beforehand. Run the test stage again; the end-user tests run as they are.
