# Opening the review would change the session from a GET, which the enforced rule DCA-HEX-014 refuses — record an exception, or let "Place Order" carry the prices the review showed?

## Question
The plan has the review's GET run a command: `ReviewPageController.Review` calls `ITakeTodaysPricesInputPort` with
`TakeTodaysPricesCommand` (`src/DcaShop.Checkout/Adapter/Incoming/Web/CheckoutCompletion/ReviewPageController.cs:42-46`),
which stores today's prices on the session. The architecture suite refuses it:
`[DCA-HEX-014] ReviewPageController.Review handles GET and drives IUseCase.ExecuteAsync with the command
TakeTodaysPricesCommand` — "map the handler to POST, PUT or DELETE, or let the GET handler ask a query". The rule is
experimental and switched on here (`tests/DcaShop.ArchitectureTests/dca-archunit.properties`,
`dca.rules.experimental = true`), so it fails the build. ADR-005 says the same in prose
(`docs/architecture/adr/adr-005-antiforgery-and-safe-methods.md:23`, "A use case that changes state is reached only
through an unsafe method").

The story's note expects a state-changing GET ("A step page's GET then changes an existing session a second time (the
first is the resume after a login) — the plan names it where that exception is recorded"). The first one,
`ResumeCheckout`, passes the rule only because it is called through a second class (`CheckoutStepPage.cs:269-272`),
which the rule does not follow (catalog `rule/hexagonal/dca-hex-014.md`, ".NET reading": "a command reached through a
second class is not followed"). It is not recorded as an exception anywhere in the rule configuration.

Everything else is built and green: the pricing no longer refuses a changed price, the session takes today's prices,
the unit and port tests pass.

## Options
- a: Record the exception: an ignore entry for `ReviewPageController.Review` under DCA-HEX-014 in
  `tests/DcaShop.ArchitectureTests/dca-archunit.properties`, and ADR-005 and ADR-012 amended to name the two
  step-page GETs that change a session. The design and tests stay as they are. Cost: an enforced rule is switched off
  for one handler; a cross-site link or a prefetch of `/checkout/review` reprices the visitor's open checkout to the
  shop's current prices (what the review would show them anyway).
- b: No state-changing GET. Opening the review asks a query that shows the session at today's prices and changes
  nothing; the review's form posts the unit price it showed for each line, and "Place Order" (a POST) takes each shown
  price when it equals the line's own or today's price, else refuses. The plan changes (the use case becomes a query,
  `ConfirmCheckoutCommand` gains the shown prices) and so do the two port tests of this story; ADR-005 holds as it is.
  Cost: a larger change, and a price that moved again after the review was opened refuses "Place Order".
- c: Call `TakeTodaysPrices` through `CheckoutStepPage`, as `ResumeCheckout` is called: the rule does not see it and
  the build passes. Cost: the rule is evaded rather than answered, and the next agent cannot tell an exception from an
  oversight — a determinism gap.

## Recommendation
b — it keeps the agreed rule (ADR-005, DCA-HEX-014) without an exception and says the story's rule literally: "Place
Order" orders at the prices the review showed, because the form carries them. a is the cheaper honest answer if a
GET that reprices is acceptable; c is not recommended.

## Answer
answer: correction: none of a/b/c — the review's GET stays a read and shows today's prices; "Place Order" carries a fingerprint of everything the review showed (lines with product, quantity and unit price, buyer details, delivery address, shipping method and price, payment method, total) and works out the same at that moment; a different result refuses the order and the review shows today's. No DCA-HEX-014 exception; what was built to store prices on the GET goes. The story is rewritten accordingly (2026-10-21).
