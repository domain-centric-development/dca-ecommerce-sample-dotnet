# A form post without its token is refused with 400 today, the adopted story says 403 — which holds?

## Question

The story is `status: adopted`: it must describe behaviour the shop already has. All three scenarios say
"Then the shop answers 403". The shop refuses a token-less form post, but with **400 Bad Request**:

- `src/DcaShop.Web/TokenOnlyAwareAntiforgeryFilter.cs:43` — `context.Result = new BadRequestResult();`, with the
  comment that this is the answer the framework's own `AutoValidateAntiforgeryTokenAttribute` gives.
- `tests/DcaShop.IntegrationTests/AccountFlowTest.cs:160` `LoggingInWithoutAnAntiforgeryTokenIsRejected` asserts
  `HttpStatusCode.BadRequest` for `/login`.
- `tests/DcaShop.IntegrationTests/ShopFlowTest.cs:100` `PostWithoutAntiforgeryTokenIsRejected` asserts
  `HttpStatusCode.BadRequest` for `/cart/add-product` (out of this story's scope, but the same filter).

The rest of each scenario holds on today's code: the login, registration and logout actions
(`src/DcaShop.Account/Adapter/Incoming/Web/LoginPageController.cs:48`, `RegisterPageController.cs:42`,
`LogoutPageController.cs:18`) carry no `[IgnoreAntiforgeryToken]`, so the global filter
(`src/DcaShop.Web/Program.cs:16`) stops them before they act. Only the status code differs. The story has no
`## Changed expectations`, and adopt mode plans no production change, so the plan cannot settle this.

## Options

a. **The code holds — 400.** Change the story's three "Then the shop answers 403" to 400 and adopt it as it stands.
   The existing test for `/login` maps to the first scenario; registration and logout get new integration tests
   asserting 400.
b. **The story holds — 403.** Then this is not an adoption but a change of agreed behaviour: the story becomes
   `ready` (not `adopted`) with a `## Changed expectations` naming the two tests above, the filter answers 403
   (the Java sample's Spring Security CSRF refusal answers 403 — worth checking, since the scenarios are shared),
   and both samples land the same code.
c. **Phrase it status-neutral.** "Then the shop refuses the post" (a 4xx, nothing done) — adoptable as is, but it
   leaves a twin-sample difference in the status code undetected.

## Recommendation

b if the Java sample answers 403 (the story's wording suggests it was written from that side, and the twins should
answer alike — a determinism gap is closed at the source); otherwise a. Either way, decide it once for both samples
and the shared specification.

## Answer
answer: b — the Java shop answers 403 (it adopted these three scenarios as written). The .NET shop is brought in line by a change story, forms-refuse-a-post-without-token-with-403, which this story depends on. This story stays adopted as written.
