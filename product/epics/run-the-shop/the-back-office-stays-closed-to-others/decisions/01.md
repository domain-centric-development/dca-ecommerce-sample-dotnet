# `/backoffice/settings` is not sent to the login in this shop — how is login-after-a-redirect-opens-the-event-log adopted?

## Question
The story is `status: adopted`: every scenario must describe what the shop already does. The Given of
`login-after-a-redirect-opens-the-event-log` — "a browser that opened `/backoffice/settings` and was sent to the
backoffice login page" — does not hold in the .NET shop:

- the back office's only routes are `login`, `logout`, `events` and `events/{id}/replay`
  (`src/DcaShop.Backoffice/Adapter/Incoming/Web/EventPublicationPageController.cs:22-76`); there is no `settings`;
- the gate is the controller's `[Authorize(AuthenticationSchemes = …)]` (`EventPublicationPageController.cs:23`), so it
  covers only routed actions. An unrouted path has no endpoint and nothing to authorize, and it ends on the 404 page
  (`src/DcaShop.Web/Program.cs:86`, `UseStatusCodePagesWithReExecute`). There is no fallback policy (no
  `FallbackPolicy` in `src/`);
- the Java sample guards the whole prefix (`securityMatcher("/backoffice/**")`,
  `dca-ecommerce-sample-java/…/backoffice/infrastructure/BackofficeSecurityConfiguration.java:56`). That is why the
  replay story (`OPS-04`) can name a page that doesn't exist.

The When/Then still hold: a successful login always redirects to `/backoffice/events` (`EventPublicationPageController.cs:59`).
Only the Given differs. A plan stage may not rewrite the story or invent behaviour, and an adoption builds nothing.

## Options
- a: change the scenario's Given to a page the shop does guard, e.g. "a browser that opened `/backoffice/events` and
  was sent to the backoffice login page", which the shop does today (the login answers with `?ReturnUrl=%2Fbackoffice%2Fevents`).
  It stays adopted and gets a characterization test. The Java twin's story and the replay text stay as they are; this
  becomes a recorded difference between the two shops.
- b: take `login-after-a-redirect-opens-the-event-log` out of this story. Adopt the other four scenarios and write a
  new (non-adopted) story that has the .NET back office guard the whole `/backoffice/**` prefix the way Java does,
  this scenario included.
- c: turn this story into a delivery (`status` other than `adopted`) that builds the prefix-wide guard, e.g. a
  fallback authorization for `/backoffice/**` under the backoffice scheme. That adds behaviour: unknown back-office
  paths send a visitor to the login instead of a 404.

## Recommendation
b. Both shops should answer an unknown back-office path the same way, and the replay story describes Java's
answer. That is new behaviour for .NET and belongs in a story of its own, not hidden inside an adoption. Option a is
cheaper, but it bakes the twins' difference into the backlog.

## Answer
answer: b — the Java shop is right. The .NET shop is brought in line by a change story, back-office-guards-every-address (every address below /backoffice asks for the operator login, login-after-a-redirect-opens-the-event-log as written), which this story depends on. This story stays adopted as written, all five scenarios, and is adopted once that story is delivered.
