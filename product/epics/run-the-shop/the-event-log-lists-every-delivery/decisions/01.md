# An incomplete entry's badge reads its status, not "Incomplete" — how is the story adopted, and may the happy path strengthen the existing browser test?

## Question
The story is `status: adopted`, so every scenario has to describe what the .NET shop already does. Two points stop the plan.

**1. The badge "Incomplete" is not what the shop renders.** `entry-shows-listener-state-and-dates` and
`counts-add-up` name a badge "Completed" or "Incomplete". The .NET view writes "Completed" for a completed entry. For
any other entry it writes the publication status: `Staged`, `Pending` or `Failed`
(`src/DcaShop.Web/Views/Backoffice/Events.cshtml:47`, `StatusLabel` from
`src/DcaShop.Backoffice/Adapter/Incoming/Web/EventPublicationPageViewModel.cs:49`; the values come from
`src/DcaShop.SharedKernel/Infrastructure/Events/IntegrationEventPublication.cs:8`). The view also uses that label to
offer the retry button (`Events.cshtml:67`). The Java sample writes the literal "Incomplete"
(`dca-ecommerce-sample-java/src/main/resources/templates/backoffice/events.pug:39`). On start-up data every entry is
usually completed, so a test would pass today. But it would only pass because nothing is incomplete. While the
dispatcher has not run yet (`src/DcaShop.Infrastructure/Events/IntegrationEventDispatcherService.cs:21`), the page shows
"Pending" and the test turns flaky. The sibling adopted stories `failed-deliveries-are-retried-on-their` and
`retry-a-failed-delivery` also expect the badge "Incomplete".

Related, information only: the rule "One entry per event and listener" holds in Java, which keeps one row per listener.
.NET keeps one entry per event and joins its listeners into the "Listener" field
(`src/DcaShop.Backoffice/Adapter/Outgoing/Persistence/OutboxEventPublicationLogStore.cs:42`). No criterion's clause
asserts the per-listener split, so this does not block the plan.

**2. The happy path's browser test already exists under the shared title.** The story's shared scenario
`scenario.backoffice.event-log-counts` ("Event log shows published domain events with correct counts") is carried by
`BackofficeE2eTest.EventLogShowsPublishedEvents` (`tests/DcaShop.E2eTests/BackofficeE2eTest.cs:35`). That test checks
only the *first* entry's type label (line 43), not every entry's. The story has no `## Changed expectations`. So
strengthening the test means listing it under `## Changed tests`, and that needs this record as backing. This is the
same situation decision `operator-login-to-the-back-office-01` answered with a.

## Options
For point 1:
- a: change the two scenarios' wording to what .NET shows: "a badge 'Completed', or for an incomplete entry its
  status ('Pending', 'Failed')". The story stays adopted. This becomes a recorded difference from Java, and the
  sibling stories need the same rewording.
- b: take the badge clauses out of this story. Adopt the rest, and write a new (non-adopted) story that has the .NET
  log show "Incomplete" the way Java does. The badge's status (Pending/Failed) and the retry button stay as they
  are.
- c: turn this story into a delivery that builds the "Incomplete" badge now.

For point 2:
- a: list `tests/DcaShop.E2eTests/BackofficeE2eTest.cs` under `## Changed tests`. `EventLogShowsPublishedEvents` keeps
  its title and assertions and gains "every entry has a type label". Map `log-lists-the-events-published-at-start-up`
  to it.
- b: leave the existing test unchanged and prove "every type label" at the adapter level only. The happy path then
  has no browser proof of its second clause.

## Recommendation
1b and 2a. The replay story describes Java's page, and both shops should look the same to an operator. Showing
"Incomplete" is new behaviour for .NET, so it belongs in a story of its own and not inside an adoption. 1a is cheaper,
but it writes the difference between the twins into three stories. 2a follows the precedent of
`operator-login-to-the-back-office-01`.

## Answer
answer: Point 1: b, as one story — the Java shop is right. The .NET shop is brought in line by a change story, event-log-marks-incomplete-deliveries (entry-shows-listener-state-and-dates and counts-add-up as written: the badge "Incomplete" for every entry that has not completed), which this story and failed-deliveries-are-retried-on-their and retry-a-failed-delivery depend on. This story stays adopted as written. Point 2: a — list tests/DcaShop.E2eTests/BackofficeE2eTest.cs under ## Changed tests; EventLogShowsPublishedEvents keeps its title and gains "every entry has a type label".
