# Which browser test proves login-opens-the-event-log without breaking the shared-scenario rule?

## Question
The judge asked. The test stage added a second browser test for the happy path,
`BackofficeLoginE2eTest` with `DisplayName = "Login opens the event log"`
(`tests/DcaShop.E2eTests/BackofficeLoginE2eTest.cs:18`). No scenario in the shared specification has that title.
The story's own note points at `scenario.backoffice.login-shows-event-log`, whose title is "Login as admin and
view the event log" (`dca-sample-specification/scenarios.md:169-174`). `BackofficeE2eTest.LoginAndViewEventLog`
(`tests/DcaShop.E2eTests/BackofficeE2eTest.cs:23`) already carries that title. The project rule (AGENTS.md, "Shared
semantics since WP-39") says a browser test implements exactly one scenario of the specification. Run with
`-p:SpecificationPath=…`, `SharedScenariosTest` fails on a test without a scenario. The existing test does not
assert the heading "Event Publication Log" or the three counter labels, so it does not prove the criterion either.

The test stage cannot fix this alone. Strengthening the existing test changes a test that existed before
(`tests-kept`), so the plan has to list it under `## Changed tests`. Adding a scenario changes the specification,
and the person owns its semantics.

## Options
- a: The plan lists `BackofficeE2eTest.LoginAndViewEventLog` under `## Changed tests`, backed by
  login-opens-the-event-log's two clauses. The test stage adds the heading and counter-label assertions there
  (the page-object helpers already exist), deletes `BackofficeLoginE2eTest` and maps the criterion to the
  existing test (changes a test). The specification and the Java suite stay as they are.
- b: Add a new scenario titled "Login opens the event log" to `dca-sample-specification/scenarios.md` and give it
  a test in the Java suite too. This leaves two scenarios for one journey that nearly duplicate each other.
- c: Map the heading and the labels to an adapter-level integration test (POST login, follow the redirect, read
  `/backoffice/events`). Keep the existing browser test as the criterion's e2e proof without any change. Delete
  the new browser test.

## Recommendation
Option a. It proves the scenario in the browser under the title the specification already gives it. It adds no
duplicate scenario and leaves the specification untouched.

## Answer
answer: a — list BackofficeE2eTest.LoginAndViewEventLog under ## Changed tests, add the heading and counter-label assertions there, delete BackofficeLoginE2eTest and map login-opens-the-event-log to the existing test. The specification and the Java suite stay as they are.
