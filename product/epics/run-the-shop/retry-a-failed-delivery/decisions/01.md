# The .NET log has no "Retry failed listener" button and no entry per listener — how is the story adopted?

## Question
The story is `status: adopted`, so every scenario has to describe what the .NET shop already does. Two of them do not.

**1. The button reads "Retry failed consumers", not "Retry failed listener".** `failed-entry-offers-a-retry`,
`retry-completes-a-failed-delivery`, `retry-leaves-other-listeners-alone` and `failing-retry-leaves-the-entry-failed`
name the button "Retry failed listener". The .NET view writes "Retry failed consumers"
(`src/DcaShop.Web/Views/Backoffice/Events.cshtml:71`). The Java sample writes "Retry failed listener"
(`dca-ecommerce-sample-java/src/main/resources/templates/backoffice/events.pug:56`). The button also has no
`data-test` attribute, which a browser test would need to find it.

**2. There is no "other listener's entry".** `retry-leaves-other-listeners-alone` expects the other listener to have
its own entry with its own "Completed" date. The .NET log shows one entry per event: its listeners are joined into the
"Listener" field (`src/DcaShop.Backoffice/Adapter/Outgoing/Persistence/OutboxEventPublicationLogStore.cs:42`), and the
entry gets a "Completed" date only when every listener has completed
(`src/DcaShop.SharedKernel/Infrastructure/Events/InMemoryIntegrationEventOutbox.cs:97`). The behaviour underneath
does hold: the replay resets only the failed listener (`InMemoryIntegrationEventOutbox.cs:107-115`, covered by
`tests/DcaShop.IntegrationTests/RetainedDeliveryTest.cs:119`). But the page cannot show it the way the scenario
says. The spec's rule "One entry per event and listener" (`product/spec/backoffice/eventlog/scenarios.md:3`) has the
same gap. Decision `the-event-log-lists-every-delivery-01` noted it but did not resolve it.

The other three scenarios hold today. `retry-completes-a-failed-delivery` redirects to `/backoffice/events`
(`src/DcaShop.Backoffice/Adapter/Incoming/Web/EventPublicationPageController.cs:81`), sets a completion date and
updates the counts. `retry-delivers-the-original-event` keeps the stored payload (`RetainedDeliveryTest.cs:138`).
`failing-retry-leaves-the-entry-failed` leaves the entry incomplete.

## Options
- a: Same as `the-event-log-lists-every-delivery-01`: Java is right. Write a change story that brings the .NET log in
  line. It would give the button the label "Retry failed listener" (with a `data-test`) and show one entry per
  event and listener, each with its own badge, "Completed" date and retry. This story depends on it and stays
  adopted as written.
- b: Reword this story to match .NET: the button "Retry failed consumers", and `retry-leaves-other-listeners-alone`
  checked in the payload's per-listener progress lines instead of a separate entry. That records a difference
  between the twins.
- c: Make this story a delivery that changes the label and splits the entries itself.

## Recommendation
a. It follows the answer to `the-event-log-lists-every-delivery-01`: the two shops describe one shop, and the
difference is closed in the code by a change story, not written into an adoption. The label alone is small, but the
per-listener split changes the log store and the spec's rule, so it belongs in a story of its own.

## Answer
answer: a — the Java shop is right. The .NET shop is brought in line by a change story, event-log-has-an-entry-per-listener (an entry per event and listener, the button "Retry failed listener"), which this story depends on. This story stays adopted as written.
