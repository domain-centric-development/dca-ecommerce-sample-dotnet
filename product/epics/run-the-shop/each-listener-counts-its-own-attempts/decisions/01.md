# How does a story's new browser test pass SharedScenariosTest before the delivering gate writes its scenario into product/spec?

## Question
The judge asked. The story's change is unchanged since the previous round and its two mapped tests pass. The
integrate gate still refused it: `DcaShop.UnitTests.Specification.SharedScenariosTest#EveryBrowserTestIsAScenarioOfThisShopsSpecification`
fails with `["Each listener counts its own attempts"]` (`.dca-factory/runs/each-listener-counts-its-own-attempts/.gate-integrate.txt:17-23`).
The main line's commit 96e95f8 emptied `TitledAfterTheSharedSpecification`
(`tests/DcaShop.UnitTests/Specification/SharedScenariosTest.cs:25`). Since then, every browser test's `DisplayName` has to be a
scenario title that is already in `product/spec/**/scenarios.md` (`SharedScenariosTest.cs:43`). This story's happy-path
browser test carries the title that its criterion key gives in words (`tests/DcaShop.E2eTests/BackofficeAttemptsE2eTest.cs:27`).
That scenario only enters `product/spec/backoffice/eventlog/scenarios.md` when the delivering gate merges the spec delta, and
that happens after the integrate suite has run. No stage may write `product/spec`. So any story that brings a new browser
test fails integrate, and this one cannot get through by changing its own code. The answer changes the project's check or
the pipeline's order, and either one is a decision nobody has taken yet.

## Options
- a: SharedScenariosTest also accepts the titles of criteria in stories under `product/epics/` that are released or
  adopted but not yet delivered, i.e. the scenarios that are about to enter the spec (changes a test outside this story; a project change).
- b: the pipeline merges the story's spec delta into `product/spec` before the integrate and delivery suites run, so the
  check sees the scenario the story brings (a dca-factory change, no project test changes).
- c: this story drops the browser test and proves its happy path at integration level, like its second criterion
  (changes the plan's level and deletes a test; it conflicts with the judge's rule that the happy path gets a browser
  test, and every later story with a browser test hits the same wall).

## Recommendation
b. The check is right that a browser test is a scenario. The trouble is that the scenario becomes visible only after the
check has run, and b fixes that order in one place, for every story. a would work too, but the guard would then have to
read the backlog.

## Answer
answer: SharedScenariosTest also knows the titles of the stories not yet delivered (their `####` criteria, title = Title line else the key in words); the spec stays the only source for the Test-line and duplicate checks. Fixed on main in 2ea4aaa; nothing changes in this story — run the stage again as it is.
