# The payload's first line is not "Status: COMPLETED, attempts: 1" in this shop — how is payload-starts-with-status-and-attempts adopted?

## Question
The story is `status: adopted`, so every scenario has to describe what the .NET shop already does. The first two
scenarios hold: the view renders every payload in a closed `<details>` with the summary "Event Payload"
(`src/DcaShop.Web/Views/Backoffice/Events.cshtml:74`), and `BackofficeE2eTest.EventPayloadCanBeExpanded`
(`tests/DcaShop.E2eTests/BackofficeE2eTest.cs:80`) expands the first one and finds it not empty.

`payload-starts-with-status-and-attempts` does not hold:

- the .NET payload begins `Status: {publication.Status}` and then the event's JSON on the next line
  (`src/DcaShop.Backoffice/Adapter/Outgoing/Persistence/OutboxEventPublicationLogStore.cs:50`). The status is the
  enum's name, `Completed` (`src/DcaShop.SharedKernel/Infrastructure/Events/IntegrationEventPublication.cs:8`), not
  `COMPLETED`, and the line has no `, attempts: <number>`;
- the .NET `Attempts` counts *failed* deliveries
  (`src/DcaShop.SharedKernel/Infrastructure/Events/IntegrationEventPublication.cs:10`), so a delivery that succeeded
  on its first try counts 0, not 1;
- the Java sample writes `"Status: " + STATUS + ", attempts: " + COMPLETION_ATTEMPTS`
  (`dca-ecommerce-sample-java/…/backoffice/adapter/outgoing/persistence/JdbcEventPublicationLogStore.java:43-48`),
  where the attempts count every try, the successful one included.

The second clause holds: the lines after the status hold `ProductCreatedEvent`'s eventId, occurredOn, productId,
amount, currency and initialStock (`src/DcaShop.Product/Events/ProductCreatedEvent.cs:17-22`). The .NET payload also
appends a per-consumer progress line after the JSON (`OutboxEventPublicationLogStore.cs:48`). The scenario does not
forbid that.

The sibling adopted story `failed-deliveries-are-retried-on-their` expects the same line format
("Status: COMPLETED, attempts: 2"). An adoption builds nothing, and a plan may not reword the story.

## Options
- a: reword the scenario to what .NET shows ("Status: Completed" and no attempts, or the failed-attempt count). The
  story stays adopted. This records a difference from Java, and the sibling story needs the same rewording.
- b: one change story (e.g. `event-payload-shows-status-and-attempts`) that brings the .NET payload's first line in
  line with Java: "Status: <STATUS>, attempts: <every try, the successful one included>", with
  payload-starts-with-status-and-attempts as written. This story and `failed-deliveries-are-retried-on-their` depend on
  it and stay adopted as written.
- c: turn this story into a delivery that builds the line now.

## Recommendation
b. This is the same shape that `the-event-log-lists-every-delivery-01` and `the-back-office-stays-closed-to-others-01`
were answered with: the Java shop is the reference, and a difference is closed in the code by a story of its own, not
inside an adoption.

## Answer
answer: b — the Java shop is right. The .NET shop is brought in line by a change story, event-payload-shows-status-and-attempts (payload-starts-with-status-and-attempts as written), which this story and failed-deliveries-are-retried-on-their depend on. This story stays adopted as written.
