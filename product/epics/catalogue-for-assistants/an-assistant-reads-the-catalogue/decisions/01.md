# Three of the five scenarios describe MCP behaviour this shop does not have — adopt the rest, or build it?

## Question
The story is `status: adopted`: it may only describe behaviour the shop already shows. Read against the code,
three scenarios do not hold, so the plan stage may not adopt them and may not plan production code either:

- **the-server-offers-two-catalogue-tools** — the tool names, descriptions and the one parameter `id` hold
  (`src/DcaShop.Product/Adapter/Incoming/Mcp/ProductCatalogMcpToolProvider.cs:37-48`), and `/mcp` is mapped without
  an authorization requirement (`src/DcaShop.Web/Program.cs:98`). But no server identity is configured
  (`src/DcaShop.Product/Infrastructure/ProductContextRegistration.cs:53` — `AddMcpServer()` without options), so the
  server introduces itself with the SDK's default (the host assembly's name), not "dca-ecommerce-sample-mcp-server" / "1.0.0".
- **an-unknown-id-returns-no-product** — `product-by-id` takes `Guid id` (`ProductCatalogMcpToolProvider.cs:48`);
  "no-such-product" is no UUID, so the call fails at argument binding instead of answering `null`. Only an unknown
  *UUID* answers `null` (`ProductCatalogMcpToolProvider.cs:51`).
- **a-blank-id-is-a-tool-error** — "" also fails at binding; nothing in the code produces the message
  "Product ID cannot be null or blank".

`all-products-lists-the-range-with-price-and-stock` and `product-by-id-returns-the-product` hold on today's code
(ordinal name order: `src/DcaShop.Product/Adapter/Outgoing/Persistence/InMemoryProductRepository.cs:53`; fields:
`src/DcaShop.Product/Adapter/Incoming/Api/ProductDto.cs`). No test covers any MCP behaviour yet (no match for `Mcp` under `tests/`).

The scenarios are the Java sample's behaviour (replay `MCP-01`); the two samples differ here — a determinism gap
between them, which is the user's call (root `AGENTS.md`, rule 1: ask which side is correct).

## Options
- a: Adopt only the two scenarios that hold; move the other three into a new, non-adopted story (status ready) that
  builds them — server identity, a string `id`, the blank-id refusal — so .NET matches Java.
- b: Turn this story itself from `adopted` into a story to build (status ready): the plan then plans the three
  changes in the MCP adapter and its registration, and the test stage writes red tests for them.
- c: Declare .NET correct: rewrite the three scenarios to what the shop does (default server identity, a UUID `id`,
  a binding error for a non-UUID) and change the Java sample and the shared specification to match.

## Recommendation
b — the story then carries one coherent behaviour across both samples and stays one story; the change is small and
confined to the incoming MCP adapter and its registration. a is equally sound if adopted stories must stay
change-free by policy.

## Answer
answer: b, as a story of its own — the Java shop is right. The .NET shop is brought in line by a change story, assistant-tools-name-their-server (server identity "dca-ecommerce-sample-mcp-server" 1.0.0, a string id, an unknown id answers null, a blank id is the tool error "Product ID cannot be null or blank"), which an-assistant-reads-the-catalogue depends on. This story stays adopted as written and is adopted once that story is delivered.
