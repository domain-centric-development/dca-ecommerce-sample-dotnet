# Two of the story's scenarios already hold — take them out, adopt them, or reword them?

## Question

`an-outside-return-page-opens-the-cart-after-login` and `a-scheme-relative-return-page-opens-the-cart-after-login`
hold on today's code, so no red test can be written for them and the test gate refuses a green one.

- The login hands any return page on to the step after it
  (`src/DcaShop.Account/Adapter/Incoming/Web/LoginPageController.cs:80-86`), but that step follows it only when it is a
  page of the shop: `CartMergePageController.Destination` uses `Url.IsLocalUrl`
  (`src/DcaShop.Cart/Adapter/Incoming/Web/CartRecovery/CartMergePageController.cs:144-145`). `IsLocalUrl` refuses
  both `https://elsewhere.example/` and `//elsewhere.example/`.
- For a browser with an empty cart the merge step redirects at once through `Destination` with "Welcome back!"
  (`CartMergePageController.cs:70-73`) — exactly the two scenarios' `Then`.
- That code came with the delivered story `only-the-browsers-own-guest-cart-is-taken-over` (commit 2752ab1), whose
  scenario `an-outside-return-page-after-the-merge-opens-the-cart` covers only the merge page
  (`tests/DcaShop.IntegrationTests/CartRecoveryOnLoginTest.cs:226`). Its `## Out of scope` left the login that needs
  no merge page to this story — but its `Destination` change already serves that path too. No story's scenario and
  no test carries the no-merge path; only code does.
- `the-register-link-drops-an-outside-return-page` does not hold yet
  (`src/DcaShop.Web/Views/Account/Login.cshtml:34` carries any return page on) and is unaffected by this question.

The Java shop was not checked from here; the spec is shared, so whatever is chosen lands in both shops' `product/spec`.

## Options

- a: Take the two login scenarios out of this story into an adopted story of their own, and build only the register link here.
    The adopted story maps both scenarios to tests, each with a break (the old `Destination`); this story keeps
    `the-register-link-drops-an-outside-return-page`, which then needs a happy-path mark of its own.
- b: Drop the two login scenarios from the story altogether, and build only the register link here.
    The behaviour stays carried by code alone, with no scenario in `product/spec/account/signin` and no test.
- c: Reword the two scenarios so they ask for what the login does not do yet: the login itself drops an outside return page.
    Their `Then` would name the login's own redirect (no return page handed to the step after it), which a customer
    does not see on a page; it would be an integration test on `LoginPageController`, not an end-user one.

## Recommendation

a — the behaviour is real and worth stating in the spec, but this story cannot prove it red; adoption records it
with a break per test, and the register link, the one change still missing, is delivered here.
