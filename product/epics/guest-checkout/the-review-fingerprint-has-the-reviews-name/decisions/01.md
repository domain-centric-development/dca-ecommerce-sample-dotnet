# May the existing fingerprint unit test name the renamed type in its assertions?

## Question
The story renames `OrderFingerprint` to `ReviewFingerprint` and says a test that existed before stays as it is.
`tests/DcaShop.UnitTests/Checkout/OrderFingerprintTest.cs` names the old type in two assertions (lines 62-63:
`OrderFingerprint.From(sent)`, `OrderFingerprint.From(order.Value)`) and in its helper (line 67, 80). It cannot compile
without the rename, so the build changed those lines to `ReviewFingerprint.Of(...)` and built the helper's fingerprint
through `CheckoutReview.Fingerprint()`; every test name, case and expected value stays. The build gate's `tests-kept`
refuses a pre-existing test whose assertion lines changed unless the plan's `## Changed tests` cites a decision — the
story has no `## Changed expectations`, and a task has none. What the test expects did not change; the name it uses did.
Deciding that a type rename may touch an existing test's lines is not the stage's call.

## Options
- a: The test follows the rename: the two assertions call `ReviewFingerprint.Of` instead of `OrderFingerprint.From`,
  the helper takes the fingerprint from a `CheckoutReview`; names, cases and expected values stay (changes a test's
  lines, not what it asserts; the build already holds this shape).
- b: `OrderFingerprintTest.cs` stays byte for byte, so an `OrderFingerprint` type with `Of` and `From` is kept beside
  `ReviewFingerprint` for the test's sake (contradicts the story's first sentence; dead production code).
- c: The old test is replaced by `ReviewFingerprintTest.cs` in the unit project with the same cases under the review's
  name (changes a test: a file removed and one added; the integration project already has a test of that name).

## Recommendation
a — it is the only reading under which the story's rename and its "a test that existed before stays as it is" both
hold: the test keeps every expectation and only spells the type as the story names it.
