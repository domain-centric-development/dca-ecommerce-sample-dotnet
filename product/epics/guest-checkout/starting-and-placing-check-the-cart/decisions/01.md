# The story is `adopted`, but three of its five scenarios do not hold on today's code — build them, reword them, or split?

## Question

Adopt mode needs every scenario to be behaviour the shop already has. Reading the code, two hold and three do not:

| Scenario | Today | Evidence |
| --- | --- | --- |
| cart-shows-cannot-checkout-when-stock-ran-short | holds — disabled "Cannot Checkout" and the note; no test covers it | `src/DcaShop.Web/Views/Cart/View.cshtml:77`, `src/DcaShop.Cart/Adapter/Incoming/Web/Shopping/CartPageController.cs:96` |
| start-from-an-outdated-cart-page-is-refused | **does not hold** — the use case throws `InvalidOperationException`, which the controller does not catch, so the visitor lands on the error page; `CheckoutItemsUnavailableException` (whose page wording is the story's sentence) is never thrown | `src/DcaShop.Checkout/Application/Session/StartCheckout/StartCheckoutUseCase.cs:65`, `src/DcaShop.Checkout/Adapter/Incoming/Web/CheckoutPageController.cs:79`, `src/DcaShop.Web/Program.cs:62` |
| start-from-an-emptied-cart-is-refused | **wording differs** — the cart page shows "Cannot check out an empty cart.", not a text beginning "Cannot checkout empty cart" (that is the exception's log message, which never reaches the page) | `src/DcaShop.Checkout/Adapter/Incoming/Web/CheckoutPageController.cs:178`, `docs/architecture/refusal-wording.md:117` |
| place-order-is-refused-when-stock-ran-short | **URL differs** — the refusal re-renders the review view as the answer to `POST /checkout/confirm`, so the browser stays at `/checkout/confirm`, not `/checkout/review`; error, no confirmation, unchanged stock and cart hold | `src/DcaShop.Checkout/Adapter/Incoming/Web/CheckoutPageController.cs:113`, `:166`, `src/DcaShop.Web/Views/Checkout/Review.cshtml:57` |
| place-order-is-refused-when-sold-out | **URL differs**, as above | same |

No test in `tests/` asserts any of the five (no use of `cart-checkout-disabled`, `cart-error-message` or `review-error-message` after a stock refusal).

## Options

1. **Make it a build story** (status back to ready, not adopted): the start refuses short stock with `CheckoutItemsUnavailableException` so the cart page shows "Cannot start checkout, 1 item(s) unavailable or out of stock."; a refused Place Order redirects to `/checkout/review` with its error. Reword the empty-cart scenario to the shop's agreed sentence "Cannot check out an empty cart." (`docs/architecture/refusal-wording.md`).
2. **Reword the story to today's behaviour and keep it adopted**: empty-cart text "Cannot check out an empty cart.", review refusal at `/checkout/confirm`; the outdated-page scenario cannot be reworded honestly (an error page is a defect), so it would leave the story.
3. **Split**: adopt cart-shows-cannot-checkout and the two place-order scenarios (with the URL clause reworded or dropped); move start-from-an-outdated-cart-page and start-from-an-emptied-cart into a new build story.

## Recommendation

Option 1. The outdated-page path is a real defect (an uncaught refusal ends on the error page) that a story should fix, the empty-cart wording should follow the one refusal wording the project agreed on, and the URL clause is cheap to honour with a redirect. Whatever is chosen, the story file is yours to change; the plan runs again on the answer.

## Answer
answer: Split by side: start-from-an-emptied-cart-is-refused now names today's sentence "Cannot check out an empty cart." (the story text is changed in both shops and the replay source, the shops' one refusal wording); the outdated cart page and the review's address after a refused Place Order are the Java shop's behaviour, brought to the .NET shop by the change story stock-checks-answer-on-the-page, which this story depends on. This story stays adopted, all five scenarios.
