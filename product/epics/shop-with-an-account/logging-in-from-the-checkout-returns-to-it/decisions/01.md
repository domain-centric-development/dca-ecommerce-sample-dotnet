# How does the account get a checkout after a login from the buyer step — a fresh one, or the guest's?

## Question

A registration from the buyer step keeps the checkout because the identity stays the same
(`src/DcaShop.Account/Adapter/Incoming/Web/RegisterPageController.cs:76`). A login replaces it with the account's
(`src/DcaShop.Account/Adapter/Incoming/Security/JwtIdentitySession.cs:37`), the take-over copies the guest's lines
into the account's cart as new positions and deletes the guest cart
(`src/DcaShop.Cart/Application/CartRecovery/RecoverCart/RecoverCartUseCase.cs:61-69`), and the guest's open session
stays keyed on the guest and the deleted cart. The buyer step looks up the session by the current customer only
(`src/DcaShop.Checkout/Adapter/Incoming/Web/CheckoutCompletion/CheckoutStepPage.cs:252`), so it sends the account to
the cart. Nothing that exists today can give the account a session synchronously:
- the take-over is Cart's page (`src/DcaShop.Cart/Adapter/Incoming/Web/CartRecovery/CartMergePageController.cs:110`)
  and a web adapter calls only its own context; Cart calling Checkout would close a cycle (Checkout already reads
  Cart, `product/domain.md:63`);
- Account depends on no other context (`product/domain.md:70`);
- integration events reach Checkout after the redirect, not before it;
- a step page that starts a session on a GET contradicts `buyer-step-without-a-checkout-leads-to-the-cart`
  (`product/spec/checkout/steps/scenarios.md:120`) and "starting a checkout creates a session — never reachable
  through a link" (`src/DcaShop.Checkout/Adapter/Incoming/Web/Session/StartCheckoutPageController.cs:29`).

Each way that works adds a surface or a relationship the story does not name, and the Java sample has to build the
same one (the story is to be built in both shops), so it is asked once, here.

## Options

- a: The account starts a fresh checkout from the taken-over cart, sent by the browser.
  After the take-over, a return address on the checkout leads to a Cart page that sends the cart page's own
  "Proceed to Checkout" form (`POST /checkout/start` with the account's cart id) — by itself where scripts run,
  with a "Continue" button where not, as the take-over page does. The session snapshots the account's cart at
  today's prices with the account's positions, so a later order completes that cart; the guest's session stays
  behind and ends like any abandoned one. Costs: one new Cart page (a route and a view) and Cart's adapter
  recognising the checkout's address among return addresses; the steps the guest had already done are not kept
  (only the buyer step was reachable before the login link, so nothing is lost here).
- b: The guest's open session is handed to the account.
  The take-over keeps the guest cart itself (same cart id, same positions) as the account's when the account's
  cart holds nothing, and Checkout moves the open session of that cart to the account in the same request. Costs:
  a synchronous call from the take-over into Checkout — a new Cart → Checkout relationship (a cycle with
  Checkout → Cart) or a login hook in the shared kernel both contexts listen to; a change to how the take-over
  keeps a cart; keeps what the guest had entered on earlier steps.
- c: A checkout step page without a session starts one from the customer's active cart.
  Costs: a GET that creates a session; contradicts `buyer-step-without-a-checkout-leads-to-the-cart` and the three
  scenarios beside it, which a visitor with a filled cart would no longer see.

## Recommendation

a — it uses only the relationships the map already has (the cart page already posts to `/checkout/start`), keeps
the session's positions those of the cart a confirmation will complete, and adds one page in the pattern the
take-over page set; b crosses a context boundary the map forbids today, c breaks four held scenarios.

## Answer
answer: none of a/b/c — d: the checkout session belongs to the cart, not to the person. Checkout finds the session through the current customer's active cart and asks Cart (the existing Checkout → Cart direction) whether that cart belongs to the current customer. The take-over keeps the guest cart itself (same cart id, same positions) as the account's when the account's cart holds nothing, so after the login the same session is found and the person lands on the delivery step (the buyer is known now). When the two carts are merged, Cart records that guest cart X was taken over into cart Y; after the merge page the person lands on the delivery step, where Checkout follows that record (read through Cart), moves the guest's open session to the account and cart Y and captures the merged cart anew. A reload changes nothing further. This is the one place where a step page's GET updates an existing session; it never creates one, so buyer-step-without-a-checkout-leads-to-the-cart and its three neighbours hold. ADR-012 names this exception. Cart never calls Checkout. Build the same in the Java shop.
