# The story is `adopted`, but three of its scenarios describe behaviour the .NET API does not have — how do we go on?

## Question

Adopt mode builds nothing; a scenario the code does not show is not adoptable. Three scenarios differ from the code:

| Scenario | The story says | The code does | Evidence |
| --- | --- | --- | --- |
| `a-second-open-cart-is-a-conflict` | second `POST /api/carts` → `409`, problem title "Active cart already exists" | returns the existing cart with `201` (get-or-create) | `src/DcaShop.Cart/Application/Shopping/GetOrCreateActiveCart/GetOrCreateActiveCartUseCase.cs:27`, `src/DcaShop.Cart/Adapter/Incoming/Api/ShoppingCartResource.cs:59` |
| `opening-a-cart-for-the-caller`, `the-callers-active-cart-by-customer-id` | `status` "ACTIVE" | `status` "Active" (`CartStatus.ToString()`) | `src/DcaShop.Cart/Adapter/Incoming/Api/ShoppingCartDtoConverter.cs:21`, `src/DcaShop.Cart/Domain/Model/CartStatus.cs:6` |
| `removing-a-product-removes-its-line` | `DELETE /api/carts/<cartId>/items/<productId>` | the path names the **cart item id**; a product id finds no line → `404` "Position not in cart" | `src/DcaShop.Cart/Adapter/Incoming/Api/ShoppingCartResource.cs:125` (its own comment names the Java product-keyed route as the shape that would have to change) |

The other four scenarios (`adding-a-product-returns-the-cart`, `adding-the-same-product-again-adds-up`,
`reading-the-own-cart`, and `opening-a-cart-for-the-caller` apart from the status spelling) hold in
`ShoppingCartResource.cs`; no existing test asserts their success answers (only `tests/DcaShop.IntegrationTests/ApiFlowTest.cs:68`
checks the `201` and the `cartId`).

## Options

1. **Split.** Keep this story `adopted` with the scenarios the code shows; move the three differing ones into a new
   build story (`ready`) so the .NET API takes over the Java sample's shape — `409` on a second open cart,
   `"ACTIVE"`, removal keyed by product id. The samples stay one behaviour (shared semantics, AGENTS.md).
2. **Make this whole story a build story** (`status: ready`). Simpler bookkeeping, but the four scenarios that already
   hold would get green tests, which the test gate refuses — they would have to leave the story anyway.
3. **Reword the story to the .NET behaviour** (get-or-create `201`, "Active", item-keyed delete) and adopt it whole.
   The two samples then answer the same request differently — a determinism gap.

## Recommendation

Option 1. The story replays the Java sample's `API-06`; a .NET API that answers it differently is the gap to close, not
to record. Note that `409` on a second `POST` also changes `ShoppingCartResource.CreateCart`'s documented contract
("or returns the one they already have") and `ApiFlowTest.ABrowserCookieNeitherAuthenticatesAnApiCallNorIsHandedOutByOne`
does not depend on it; the build story should state that in its `## Changed expectations`.

## Answer
answer: 1 — the Java shop is right. The .NET shop is brought in line by a change story, cart-api-answers-as-the-reference (the four scenarios as written), which this story depends on. This story stays adopted as written.
