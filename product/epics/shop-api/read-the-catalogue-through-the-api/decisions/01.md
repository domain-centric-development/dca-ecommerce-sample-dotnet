# The unknown-product scenario asks for an empty 404 the API does not give — adopt the rest, or build it?

## Question
The story is `status: adopted`: it may only describe behaviour the shop already shows. Three scenarios hold on
today's code; **an-unknown-product-is-not-found** does not:

- `GET /api/products/no-such-product` matches no route — `ProductResource.GetProductById` is `[HttpGet("{id:guid}")]`
  (`src/DcaShop.Product/Adapter/Incoming/Api/ProductResource.cs:73`). The empty 404 of the unmatched route is then
  re-executed by `app.UseStatusCodePagesWithReExecute("/error/{0}")` (`src/DcaShop.Web/Program.cs:86`, applied to every
  path, `/api/**` included) into `ErrorPageController.Show`, which renders the HTML not-found view
  (`src/DcaShop.Web/Controllers/ErrorPageController.cs:12`). The answer is 404 **with an HTML page**, not an empty body.
- Even an unknown *UUID* would not answer an empty body: `NotFound()` on an `[ApiController]`
  (`ProductResource.cs:77`) is turned into a problem document by ASP.NET Core's client-error mapping.
- No test asserts either today (`tests/DcaShop.IntegrationTests/ApiFlowTest.cs:37` only reads a known id).

The three that hold: ordinal name order (`src/DcaShop.Product/Adapter/Outgoing/Persistence/InMemoryProductRepository.cs:53`),
21 seeded products with BOOK-001 54.99/20 and BOOK-005 34.99/26 (`src/DcaShop.Product/Adapter/Incoming/Bootstrap/SampleDataSeeder.cs:25`, `:29`),
the fields `id, sku, name, description, imageUrl, price, currency, category, stockQuantity, isAvailable`
(`src/DcaShop.Product/Adapter/Incoming/Api/ProductDtoConverter.cs:33`), the GET routes without `[Authorize]`.

The scenario is the Java sample's behaviour (replay `API-02`); the samples differ here — a determinism gap, the
user's call (root `AGENTS.md`, rule 1).

## Options
- a: Adopt the three scenarios that hold; move **an-unknown-product-is-not-found** into a new story (status ready) that builds it.
- b: Turn this story from `adopted` into a story to build (status ready): the plan then plans status-code pages to skip
  the token-only paths (`TokenOnlyPaths`, as the exception handler already does at `src/DcaShop.Web/Program.cs:69`),
  so an unmatched `/api/**` route answers 404 with an empty body; the test stage writes the red test.
- c: Declare .NET correct: rewrite the scenario to what the shop does (404 with the HTML not-found page) and change the
  Java sample and the shared specification to match.

## Recommendation
b — an HTML error page on a JSON API is the defect, not the Java behaviour; the fix is one condition in the host,
reusing the `TokenOnlyPaths` list the antiforgery filter and the exception handler already ask. a is equally sound if
adopted stories must stay change-free by policy.

## Answer
answer: b, as a story of its own — the Java shop is right. The .NET shop is brought in line by a change story, api-answers-an-unknown-product-plainly (an unmatched product address under /api answers 404 with an empty body), which read-the-catalogue-through-the-api depends on. This story stays adopted as written and is adopted once that story is delivered.
