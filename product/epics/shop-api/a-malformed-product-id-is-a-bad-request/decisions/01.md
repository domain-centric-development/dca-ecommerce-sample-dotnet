# How does a story's new end-user test pass `SharedScenariosTest` before the story is delivered?

## Question

The happy path's end-user test `DcaShop.E2eTests.CartApiE2eTest#AProductIdThatIsNotAUuidIsABadRequestAndLeavesTheCartEmpty`
carries the display name "A malformed product id is a bad request", the scenario's key in words, as the test gate
requires. The production code is done and every mapped test is green, but the build gate's required unit suite is red:
`tests/DcaShop.UnitTests/Specification/SharedScenariosTest.cs:43` (`EveryBrowserTestIsAScenarioOfThisShopsSpecification`)
asserts that every `*E2eTest.cs` display name is already a scenario title in `product/spec/**/scenarios.md`. The
scenario reaches `product/spec/cart/shopping/scenarios.md` only when the gate delivers the story (backlog contract,
"The living spec": the spec is merged by the delivering gate, `Test:` lines by the gate alone). So no story that adds an
end-user test can pass the build gate while this check stands as it is. `SharedScenariosTest` was introduced in
`96e95f8`; this is the first story since that adds an end-user test.

The repository's `AGENTS.md` says "A new end-user test therefore starts as a scenario in `product/spec`", which
contradicts the pipeline's rule that only the delivering gate writes the spec.

## Options

a. **The check also accepts the scenarios of stories not delivered yet**: `SharedScenariosTest` reads the titles of the
   scenarios in `product/epics/**/story.md` with a `status:` before delivery, besides `product/spec`. A test change
   outside this story, in the project's test support; the story then passes unchanged.
b. **The build writes the scenario into `product/spec/cart/shopping/scenarios.md` now**, as `AGENTS.md` says. The plan's
   spec delta (`adds`) would then disagree with the spec at the integrate gate (it would read `holds`), and a `Test:`
   line would be written by a stage, not the gate — likely refused at delivery.
c. **The title goes on `TitledAfterTheSharedSpecification` for the time of the story.** Its own assertion
   (`SharedScenariosTest.cs:45`) fails as soon as delivery merges the scenario, so the delivered tree is red until a
   person takes it off again.

## Recommendation

a — the check's purpose (no end-user test without a scenario) holds, the pipeline's ownership of `product/spec`
stays intact, and every later story adding an end-user test needs no question. The `AGENTS.md` sentence then reads
"starts as a scenario in a story". The Java twin's counterpart check, if it has one, needs the same answer.

## Answer
answer: SharedScenariosTest also knows the titles of the stories not yet delivered (their `####` criteria, title = Title line else the key in words); the spec stays the only source for the Test-line and duplicate checks. Fixed on main in 2ea4aaa; nothing changes in this story — run the stage again as it is.
